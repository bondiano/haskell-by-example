# Интерлюдия: компилятор GHC

> **Это приложение — дополнительный материал.** Оно не входит в основную линию книги и не требуется для дальнейших глав. Читайте его, если вам интересно, что происходит «под капотом» при компиляции Haskell-кода.

## Зачем знать о компиляторе

На протяжении книги мы писали код на Haskell, не задумываясь о том, как он превращается в машинные инструкции. Мы доверяли GHC: он выводил типы, оптимизировал свёртки, превращал `do`-нотацию в цепочки `>>=`. Но понимание компилятора помогает:

- **Писать быстрый код** — зная, какие оптимизации применяет GHC, можно им помогать (или не мешать).
- **Отлаживать производительность** — если программа медленная, полезно заглянуть в промежуточное представление.
- **Глубже понимать язык** — синтаксический сахар перестаёт быть магией, когда видишь, во что он превращается.

## Конвейер GHC

Путь от исходного кода до машинных инструкций проходит через восемь стадий:

```text
Haskell Source (.hs)
    |
    v
  Parse            --> синтаксическое дерево (HsSyn)
    |
    v
  Rename           --> разрешение имён, области видимости
    |
    v
  Type Check       --> вывод типов (Hindley-Milner + расширения)
    |
    v
  Desugar          --> убрать синтаксический сахар
    |
    v
  Core             --> типизированное лямбда-исчисление (System FC)
    |                   ^ оптимизации (inlining, fusion, rules)
    v
  STG              --> Spineless Tagless G-machine
    |
    v
  Cmm              --> C-подобный промежуточный язык
    |
    v
  Machine Code     --> через LLVM или собственный backend
```

Каждая стадия — трансформация из одного промежуточного представления (IR) в другое. Все ваши `do`-блоки, `where`-клозы, list comprehensions, паттерн-матчинг — «растворяются» на этапе Desugar и никогда не достигают машинного кода в исходном виде.

```admonish tip title="Знакомый аналог"
Конвейер GHC напоминает конвейер LLVM-компилятора: исходный код -> AST -> IR (LLVM IR) -> оптимизации -> машинный код. Разница в том, что GHC имеет **два** промежуточных представления до машинного уровня (Core и STG), каждое со своей ролью.

В мире TypeScript аналогия проще: `.ts` -> parse -> type check -> emit `.js`. GHC делает то же самое, но вместо «emit JS» — генерация нативного кода через несколько дополнительных IR.
```

### Parse

Парсер GHC превращает текст в синтаксическое дерево `HsSyn`. Это дерево **близко к исходному коду** — сохраняет `do`-нотацию, `where`, list comprehensions, guards.

На этой стадии проверяется только синтаксис. Имена ещё не разрешены: если вы написали `map f xs`, парсер не знает, какой именно `map` имеется в виду.

### Rename

Renamer разрешает имена: определяет, из какого модуля пришёл каждый идентификатор, проверяет области видимости, обнаруживает неиспользованные импорты. После этой стадии каждое имя — уникальный идентификатор.

### Type Check

Самая сложная стадия. GHC использует расширенный алгоритм Хиндли-Милнера для **вывода типов**. Здесь проверяются:

- Совпадение типов в выражениях.
- Корректность экземпляров классов типов.
- Ограничения `GADTs`, `TypeFamilies` и других расширений.

Если ваш код компилируется — значит, GHC доказал его типовую корректность. Это та самая гарантия «если компилируется — работает», которая делает Haskell надёжным.

### Desugar

**Десахаризация** — удаление синтаксического сахара. Это ключевой этап: богатый синтаксис Haskell сводится к крошечному Core.

## Core — сердце компилятора

**Core** — типизированное лямбда-исчисление, основанное на **System FC** (System F with Coercions). Весь Haskell с его синтаксическим богатством сводится примерно к десяти конструкциям:

```text
data Expr
  = Var   Id              -- переменная
  | Lit   Literal         -- литерал (42, 3.14, "hello")
  | App   Expr Expr       -- применение функции
  | Lam   Id Expr         -- лямбда-абстракция
  | Let   Bind Expr       -- let-привязка
  | Case  Expr Id [Alt]   -- case-выражение (единственный способ ветвления)
  | Cast  Expr Coercion   -- приведение типов (для newtype и GADT)
  | Type  Type            -- тип (стирается в рантайме)
```

Обратите внимание: **нет** `if/then/else`, нет guards, нет `where`, нет `do`-нотации, нет list comprehensions. Всё это — синтаксический сахар над `Case`, `Let`, `Lam` и `App`.

```admonish note title="Связь с лямбда-исчислением"
Core — прямое продолжение лямбда-исчисления. `Lam` — абстракция (\\x -> ...), `App` — применение (f x), `Let` — привязка имени, `Case` — единственная форма ветвления. Если вы понимаете лямбда-исчисление, вы понимаете Core.
```

## Десахаризация: во что превращается ваш код

### `do`-нотация

`do`-нотация — синтаксический сахар над `>>=` и `>>`:

```haskell
-- Исходный код
main :: IO ()
main = do
  putStrLn "Введите название задачи:"
  title <- getLine
  putStrLn ("Задача: " ++ title)

-- После десахаризации (приблизительно)
main :: IO ()
main =
  putStrLn "Введите название задачи:" >>
  getLine >>= \title ->
  putStrLn ("Задача: " ++ title)
```

Оператор `<-` превращается в `>>=` с лямбдой. Оператор-разделитель (строки без `<-`) превращается в `>>`. Мы разбирали это в [главе 12](chapter12.md).

### Паттерн-матчинг

Многоуравнения с паттернами превращаются в `case`:

```haskell
-- Исходный код
showPriority :: Priority -> String
showPriority Low    = "Низкий"
showPriority Medium = "Средний"
showPriority High   = "Высокий"

-- После десахаризации
showPriority :: Priority -> String
showPriority p = case p of
  Low    -> "Низкий"
  Medium -> "Средний"
  High   -> "Высокий"
```

Все формы паттерн-матчинга (guards, `where`, вложенные паттерны) сводятся к вложенным `case`-выражениям.

### List comprehensions

```haskell
-- Исходный код
highPrioTitles :: [Task] -> [String]
highPrioTitles tasks =
  [ taskTitle t | t <- tasks, taskPriority t == High ]

-- После десахаризации (упрощённо)
highPrioTitles :: [Task] -> [String]
highPrioTitles tasks =
  concatMap (\t -> if taskPriority t == High
                   then [taskTitle t]
                   else []) tasks
```

List comprehensions превращаются в комбинации `map`, `filter`, `concatMap`.

### `if/then/else`

```haskell
-- Исходный код
isUrgent :: Task -> Bool
isUrgent t = if taskPriority t == High then True else False

-- После десахаризации
isUrgent :: Task -> Bool
isUrgent t = case taskPriority t == High of
  True  -> True
  False -> False
```

`if` — это `case` над `Bool`. В Core нет отдельной конструкции для условий.

### `where`

```haskell
-- Исходный код
taskSummary :: Task -> String
taskSummary t = prefix ++ taskTitle t
  where prefix = "[" ++ showPriority (taskPriority t) ++ "] "

-- После десахаризации
taskSummary :: Task -> String
taskSummary t =
  let prefix = "[" ++ showPriority (taskPriority t) ++ "] "
  in prefix ++ taskTitle t
```

`where` превращается в `let ... in ...`. В Core есть только `Let`.

## Просмотр Core

GHC позволяет посмотреть Core-представление вашего кода:

```text
$ stack ghc -- -ddump-simpl -dsuppress-all -dsuppress-uniques MyModule.hs
```

Флаги:

- `-ddump-simpl` — вывести Core после оптимизаций.
- `-dsuppress-all` — убрать лишнюю информацию (типы, тикеты).
- `-dsuppress-uniques` — убрать уникальные суффиксы из имён.

Для более детального анализа:

- `-ddump-ds` — Core **до** оптимизаций (сразу после десахаризации).
- `-ddump-simpl-iterations` — Core на каждом проходе оптимизатора.
- `-ddump-stg-final` — STG-представление.

```admonish warning title="Объём вывода"
Core даже для маленького модуля — сотни строк. Начинайте с маленьких примеров (одна-две функции). Используйте `-dsuppress-all` для читаемости.
```

## Оптимизации

GHC применяет десятки оптимизаций на уровне Core. Рассмотрим ключевые.

### Inlining (подстановка)

GHC подставляет тело маленьких функций вместо вызова. Это ключевая оптимизация, потому что она открывает возможности для дальнейших преобразований:

```haskell
-- До inlining
double :: Int -> Int
double x = x + x

quadruple :: Int -> Int
quadruple x = double (double x)

-- После inlining
quadruple :: Int -> Int
quadruple x = (x + x) + (x + x)
```

Прагма `INLINE` — подсказка GHC:

```haskell
{-# INLINE double #-}
```

GHC и без прагмы инлайнит маленькие функции, но `INLINE` **гарантирует** подстановку.

### Specialization (специализация)

Полиморфные функции передают словари классов типов как дополнительные аргументы. Специализация создаёт мономорфные версии для конкретных типов, устраняя overhead словарей:

```haskell
-- Полиморфная версия (с передачей словаря Num)
sum :: Num a => [a] -> a

-- Специализированная версия (без словаря)
sum_Int :: [Int] -> Int
```

Прагма `SPECIALIZE`:

```haskell
{-# SPECIALIZE sum :: [Int] -> Int #-}
```

### Strictness analysis (анализ строгости)

GHC анализирует, какие аргументы функция **обязательно** вычислит. Для таких аргументов он может применить энергичное вычисление вместо создания санка:

```haskell
-- GHC обнаруживает, что оба аргумента (+) будут вычислены
f :: Int -> Int -> Int
f x y = x + y
-- Результат: x и y вычисляются до вызова (+), без санков
```

Это напрямую связано с [главой 9](chapter09.md), где мы разбирали `foldl'` vs `foldl`. Strictness analysis помогает GHC автоматически превращать ленивый код в строгий, когда это безопасно.

### Rewrite rules и fusion

Библиотеки могут определять правила перезаписи — алгебраические тождества, которые GHC применяет автоматически:

```haskell
{-# RULES "map/map" forall f g xs.
    map f (map g xs) = map (f . g) xs #-}
```

Это правило устраняет промежуточный список: вместо двух проходов — один. Самый важный пример — **foldr/build fusion**:

```haskell
-- Без fusion: создаётся промежуточный список
sum (map (+1) [1..1000000])

-- С fusion: GHC «склеивает» map и sum в один проход
-- Промежуточный список НЕ аллоцируется
```

```admonish tip title="INLINE для библиотечного кода"
Если ваша библиотека экспортирует маленькие функции, добавьте `INLINE` — GHC сможет оптимизировать их на стороне клиентского кода (cross-module inlining). Без `INLINE` тело функции недоступно за пределами модуля.
```

### Case-of-case

Вложенные `case`-выражения оптимизируются:

```haskell
-- До оптимизации
case (case x of { True -> A; False -> B }) of
  A -> ...
  B -> ...

-- После case-of-case
case x of
  True  -> ... -- ветка A
  False -> ... -- ветка B
```

Промежуточный `case` устраняется. Это особенно важно после inlining, когда код вкладывается друг в друга.

## Пример: как GHC компилирует функцию трекера

Рассмотрим функцию из нашего трекера задач:

```haskell
countByStatus :: [Task] -> Map Status Int
countByStatus = foldl' (\acc t -> Map.insertWith (+) (taskStatus t) 1 acc) Map.empty
```

Что делает GHC:

1. **Parse**: строит синтаксическое дерево с `foldl'`, лямбдой, `Map.insertWith`.
2. **Rename**: разрешает `foldl'` -> `Data.List.foldl'`, `Map.insertWith` -> `Data.Map.Strict.insertWith`.
3. **Type Check**: выводит типы, проверяет, что `(+)` работает для `Int`, `taskStatus` возвращает `Status`.
4. **Desugar**: секции операторов (`(+)`) разворачиваются в лямбды.
5. **Core + оптимизации**:
   - `foldl'` инлайнится (это маленькая функция с `INLINE`-прагмой).
   - Strictness analysis обнаруживает, что аккумулятор `acc` вычисляется строго (благодаря `foldl'`).
   - `Map.insertWith (+)` может быть специализирована для `Int`.
6. **STG**: лямбды превращаются в замыкания (closures) с явным управлением стеком.
7. **Cmm -> Machine Code**: финальная генерация нативных инструкций.

На выходе — эффективный машинный код, который обходит список один раз, строго вычисляя аккумулятор.

## Runtime System (RTS)

GHC компилирует в нативный код, но программа работает внутри **Runtime System** — среды исполнения.

### Green threads

Потоки в Haskell — **лёгкие** (green threads). Они мультиплексируются на несколько OS-потоков:

- Создание потока: ~1 КБ стека (vs ~1 МБ для OS thread).
- Миллионы одновременных потоков — нормальная ситуация.
- Кооперативная планировка с preemption на safe points.

```admonish note title="Историческая справка"
Go goroutines используют ту же идею (green threads + M:N scheduling), но Haskell делал это с 1990-х. Erlang — ещё раньше, с 1986 года.
```

### Сборщик мусора

GHC использует **generational, copying GC**:

- **Nursery** (generation 0): маленькая область, собирается часто и быстро. Большинство объектов умирают здесь.
- **Старое поколение** (generation 1+): объекты, пережившие несколько сборок.
- Параллельная сборка старого поколения на многоядерных процессорах.

Настройка через RTS-флаги:

```text
$ ./myprogram +RTS -N4 -A64m -H512m
--                 |    |      |
--                 |    |      +-- начальный размер heap
--                 |    +-- размер nursery (больше = реже minor GC)
--                 +-- 4 OS-потока
```

## Заключение

Мы проследили весь конвейер GHC — от разбора исходного кода до генерации машинных инструкций, через Rename, Type Check, Desugar, Core, STG и Cmm. Core оказался типизированным лямбда-исчислением из примерно десяти конструкций, в которое сводится весь богатый синтаксис Haskell. На примерах `do`-нотации, паттерн-матчинга, list comprehensions и `where` мы увидели, как работает десахаризация. Ключевые оптимизации GHC — inlining, specialization, strictness analysis, rewrite rules и fusion — превращают декларативный код в эффективные машинные инструкции.

GHC — один из самых сложных компиляторов в мире. Знать его устройство необязательно для написания Haskell-кода, но понимание конвейера помогает писать **быстрый** код: не бороться с компилятором, а сотрудничать с ним.
